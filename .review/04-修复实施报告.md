### 数据无损核查（只读，工程师执行）
- **结论**：未发现 `refresh_quality.py` 造成 `SongSource.data_json` 损坏的任何迹象（强证据，6 条独立证据链）。DB `config/music_monitor.db`（`song_sources` 188 行，其中 local 33 行）`PRAGMA integrity_check = ok`；188/188 的 `data_json` 均为合法 JSON 对象，零畸形、零字符串型；local 行中"仅含 `{quality,format}`"或"data_json 缺 `cover` 键"的记录均为 0 条（即无 `data = {}` 重置指纹）。
- **关键反证**：脚本第 56-60 行 "Force FLAC check" 会把 bare except 降级出的 `PQ` 当场抵消为 `SQ`，结构上不可能让任何 .flac 停在 PQ；而库中 id=178 至今仍是 `PQ`、id=181 是 `HQ`，说明**该脚本从未成功处理过本库**。
- **真正成因**：id=178 的 `PQ` 来自 `metadata.get('quality','PQ')`、id=181 的 `HQ` 来自 `_extract_metadata` 的兜底，均为**扫描当时 mutagen 读不出文件**（文件在下载中/未完整落盘）留下，与 refresh_quality 无关。
- **雷已拆**：`import json` 缺失的半年雷已随 `8d92f7c` 排除（见上）。当前脚本因 venv 的 mutagen 残缺安装（`from mutagen import File` 直接 `ImportError`）根本跑不起来——这本身也是个环境隐患。

### 核查中暴露的真问题（建议单独立项，本轮未改）
- **P1（双编码写入源）**：`song_management_service.py:411`、`artist_refresh_service.py:636` 往 JSON 列塞 `json.dumps(...)`（字符串）而非 dict——这是唯一能真正制造畸形 `data_json` 的源头；当前只写线上源（qqmusic/netease），暂无 local 影响，但属上游隐患。
- **P2（bare except）**：`refresh_quality.py:53` 与 `:67` 两处 bare except 应改具名异常 + 日志，解析失败时**跳过该行**而非 `data = {}`，杜绝字段抹除。
- **P3（环境 + 脏数据）**：① 修复 venv 的 mutagen 残缺安装（`pip install --force-reinstall mutagen`），它静默劣化所有音频分析路径（正是 id=181 脏数据成因）；② 重扫 id=178/181 纠正 `PQ→SQ`、`HQ→SQ`；③ id=177 与 id=178 为同一物理文件挂在两个不同 song 下（song 2「一生所爱」/卢冠廷，song 101「一生所爱」/卢冠廷, 莫文蔚），且 song 101 的 `local_path` 是反斜杠混合路径，与 `SongSource.url` 正斜杠形式不一致——需去重/路径规范化。
