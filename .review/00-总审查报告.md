## 3. ⚠️ 已在主干确认的真实缺陷（重点，已实地核验）

> 以下 5 项不是"潜在风险"，而是**现在就会出错**。其中 D-1/D-4/D-5 均为 `NameError`，ruff 一条 `F821` 规则即可全部命中；D-2/D-3 为逻辑缺陷。建议立刻接入 `ruff` 并修复，并按 QA 建议加 `MM_STRICT_ERRORS` 环境变量把"吞异常"变成 CI 可捕获信号（详见 `03-testing.md` 附录 E）。

### D-1 · `/api/profile_stats` 永远返回 0（HTTP 仍 200）
- **位置**：`app/routers/auth.py:216`（以及 `:221`）
- **事实**：函数内使用 `select(func.count(...))`，但本文件仅 `from sqlalchemy import func`，**`select` 从未导入**。该语句必然 `NameError`，被包裹的宽 `except` 吞掉 → 接口恒返回 `artist_count=0 / song_count=0 / cache_size="0 MB"`，状态码 200。
- **修复**：`from sqlalchemy import func, select`（一行）。同时收紧该 `except`，避免再次掩盖逻辑错误。

### D-2 · 去重把含 "test" 的标题误判为伴奏（永远无法去重）
- **位置**：`app/services/deduplication_service.py:23,25-29`
- **事实**：`inst_markers = ['test', 'instrumental', ...]`，用子串 `if m in t` 匹配。导致 "Protest"/"Contest"/"Latest" 等被标记伴奏 → 与正版无法合并（去重失效）。
- **修复**：将 `'test'` 从伴奏标记移除；伴奏判定改用边界词（`\btest\b` 或精确黑名单 `instrumental/inst./伴奏/karaoke/off vocal`）。

### D-3 · 连字符过度截断 → 多个标题被砍成同一短串并**互相错误合并**（数据破坏级）
- **位置**：`app/services/deduplication_service.py:37`
- **事实**：`re.sub(r'[\||－|-].*$', '', t_clean)` 删除首个 `-`（或 `|`/`－`）之后的**全部**内容。结果："A-Ha"→`a`、`Jay-Z`→`jay`、`Rock-n-Roll`→`rock`；所有被砍剩 `a` 的标题会互相合并，造成**错误的数据合并**。
- **修复**：仅在特定分隔（如 ` - ` 带空格）后截断，且对含连字符艺名（A-Ha、AC/DC 等）做保护；截断前先判等。

### D-4 · "QQ 发布时间优先"规则基本不生效（循环变量泄漏）
- **位置**：`app/services/deduplication_service.py:280-295`
- **事实**：发布时间补全复用了 `:280` 封面循环的 `item`（且 `item_sources` 来自 `:213` 的另一个循环），二者指向不同对象。结果只检查单个（甚至错误的）item，QQ 优先逻辑形同虚设。
- **修复**：在合并阶段**独立、完整地遍历 `group`** 收集各来源 `publish_time`，按规则（QQ > 其他；缺失才回退）统一选择；消除跨循环变量复用。

### D-5 · 「重新下载歌曲」「从搜索结果下载」两个核心功能当前必定 500
- **位置**：`app/services/song_management_service.py:161` 与 `:308` 调用 `_get_download_service()`（带前导下划线）；该名字**全仓库零定义**，文件 `:32` 导入的是无下划线的 `get_download_service`。
- **事实**：运行到这两行必然 `NameError`；且两方法的装饰器 `raise_on_critical` 默认 `True`，异常上抛而非降级 → 接口**直接 500**。调用链完整可达：
  - 「重新下载歌曲」：`routers/library.py:274` → `services/library.py:107` → `song_management_service.py:161` 💥
  - 「从搜索结果下载」：`routers/library.py:333` → `services/library.py:127` → `song_management_service.py:308` 💥
- **修复**：两处 `_get_download_service()` 改为 `get_download_service()`（2 行）。并全量跑 `ruff check --select F821`，不排除还有第 4、第 5 处潜伏在被 `except` 吞掉的分支中。

## 4. 优先级整改路线图

### P0 · 立即止血（≈0.5–1 人日，含 D-1~D-4 + 安全）
1. **修复 §3 主干缺陷 D-1~D-4**，并接入 `ruff`（启 `F821`/`B007`/未使用变量等）作为 CI 门禁，杜绝同类回归。
2. **音频接口鉴权 + 路径 containment**（A-17 / C-02）：`/api/audio/{filename:path}` 改为「签名 URL 或已登录会话」二选一；`FileResponse` 前用 `os.path.realpath` 校验落在 `audio_cache/`、`favorites/`、`library/` 根下，防目录穿越。
3. **配置接口脱敏**（A-03 / C-01）：`GET /api/settings`、`/api/system` 禁止直接 `return _config`；新增 `_public_view()` 对 `secret_key`/`password`/`corpsecret`/`bot_token` 脱敏（或 `set`/`unset` 标记）。
4. **密钥/口令外置与哈希**（A-01 / C-17 / A-21）：`secret_key`、三方凭证移出可被 API 回显的 YAML，改环境变量/密钥文件（0600）；管理员口令强哈希（bcrypt/argon2），去除明文比较。

### P1 · 治本（≈1 周）
5. **统一配置真相**（A-02/A-03/A-20/C-05）：废弃 `core/config.py` 的全局 `config` 字典，所有读写走 `get_config_manager().get(...)`；`external_url` 统一为 `system.external_url`；`get_secret_key()` 与 `SessionMiddleware` 共用同一取值路径。
6. **鉴权改默认拒绝**（A-18）：以 FastAPI `Depends(require_auth)` 显式标注需鉴权端点，白名单仅保留 `login/callback/health` 等真正匿名端点；`/api/test_notify_card`、`/api/discovery/probe_qualities` 等移除白名单或加独立管理员令牌。
7. **签名 URL 收敛**（A-19）：TTL 可配置且默认缩短（如 1h），引入一次性消费/已用记录防重放。
8. **后台任务接管**（A-23/C-08）：禁用 `asyncio.create_task` 即忘式派发，改经 APScheduler `add_job` 或持久化任务队列（DB 任务表 + worker），任务可观测、可重试、重启可恢复。
9. **依赖锁 + 消除双重建表 + 统一引擎**（A-12/A-13/A-28）：以 Alembic 为唯一建表来源（移除 `create_all`）；`ConfigManager` 复用应用引擎而非自建；生成 `requirements.lock`，CI 校验 hash。
10. **全局 HTTP 超时 + SSRF 防护**（C-04/C-06）：定义统一 `ClientTimeout(total=15, connect=5)` 常量，所有出站 HTTP 必带（通知类加熔断）；封面/播放/代理 URL 做域名白名单 + 内网 CIDR 校验 + 重定向校验。
11. **异常可观测 + 响应脱敏**（C-03/C-15）：裸 `except:` / `except Exception: pass` 全量改为 `logger.error(..., exc_info=True)`；`general_exception_handler` 只返回泛化文案 + `request_id`，细节落日志。

### P2/P3 · 模块边界、性能与可运维增强
12. **拆分上帝对象**（A-08）：`scan_service.py`（927 行）按职责拆 `LocalScanner`/`MetadataEnricher`/`Deduplicator`/`Ingestor`，各自可测。
13. **路由归并**（A-09）：配置/下载等跨模块同名路由收敛到单一模块，消除重复定义。
14. **SQLite 并发**（A-14）：建库后 `PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000;`。
15. **抽统一 `QualityResolver` / `DedupMerger`**（C-11）：消除音质/去重逻辑在 3 处重复实现。
16. **技术债清理**（C-12/13/14、A-31）：`scripts/` 约 26 个调试脚本移入 `tools/` 并加 `--dry-run` 守卫、CI 禁止入生产镜像；噪声/emoji/PII 日志治理；新增 `GET /api/health` 探针。

## 5. 测试体系重建（来自 QA，关键"制度性根因"）

**现状（实测）**：
- 后端约 15,000 行，自动化测试 **9 个函数**（其中 1 个函数体是 `pass`），估算**行覆盖率 ≈3%**；Routers **0/14（0%）**、Repositories/Core/Notifiers/Utils/Models 全 0。
- `测试/` 目录 23 个用例中 **19 个是"mock 完对象再断言 mock 自己"的假测试**（如 `test_api_integration.py:43-65` 断言自己设的返回值），一行生产代码都没跑；`test_acceptance.py:209` 甚至"断言 dict 里有自己刚写进去的 key"。
- **`requirements.txt` 里连 `pytest` 都没有**；CI 只有 `docker-publish.yml`，**PR 不跑任何测试** → 干净环境无法复现测试。

**根因（git 取证）**：commit `f7bd209` 一次性删除了 `tests/services/` 下约 140 个测试（含 `test_smart_merger.py` 23 例 0 失败、`test_song_management_service.py` 16 例其中 13 例红灯、`test_favorite_service.py` 9 例 6 例红灯、`test_artist_refresh_service.py` 9 例）——**用删测试来"修复"红灯**。

**可落地第一步（最高优先级，≈2 人日，立刻止血）**：
1. **第 0 步地基（0.5d）**：SAVEPOINT 隔离版 `conftest`（`join_transaction_mode="create_savepoint"` 替代假 rollback）、`_isolate_global_state` autouse fixture、`requirements-dev.txt`（含 pytest/pytest-asyncio/respx/aioresponses/pytest-mock/ruff）、`test.yml` CI（覆盖率棘轮 + `docker-publish` 加 `needs: pytest`）。
2. **恢复历史单测（1d）**：从 `f7bd209^` 复活 `test_smart_merger.py` 等（0 失败，几乎零成本），有效用例 8 → 约 65。
3. **P0 补测（按优先级）**：auth/鉴权中间件 → 微信指令分发与验签 → download_service → favorite_service → notification → 去重缺陷回归（D-2/D-3/D-4）→ settings 持久化。项目已有干净注入点 `core.database.get_async_session`，API 测试可零改造接入。

**Mock 策略红线**：respx(httpx) / aioresponses(aiohttp) / monkeypatch(pyncm·qqmusic SDK) / 真 SQLite 不 mock ORM / tmp_path / freezegun。**把被测模块整个删掉，测试必须变红**——否则即为假测试，应删除。
