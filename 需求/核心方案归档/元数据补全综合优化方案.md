# 元数据补全综合优化方案

## 1. 背景与问题定位
系统在自动补全歌曲元数据时存在失败情况，而手动补全能成功。核心差异在于：
1. **冷却期限制不合理**：元数据获取使用网易云和QQ音乐接口（无频次限制），却错误地套用了 GDStudio 的 24 小时冷却期。
2. **搜索策略单一**：未能智能处理标点符号和变体，只有标题+歌手的精确搜索。
3. **重试机制薄弱**：固定 3 次指数退避，不足以应对网络波动。

## 2. 优化方案实施细节

### 2.1 移除不必要的冷却期限制
元数据补全接口无严格频率限制，**只保留下载与维护操作的冷却期**。
- `OperationType.METADATA_FETCH`：0秒（无冷却）
- `OperationType.AUDIO_DOWNLOAD`：300秒（5分钟，受 GDStudio 限制）

### 2.2 多轮渐进式搜索策略
实施智能重试，根据优先级降级搜索：
1. **精确匹配** (`title + artist`)
2. **关键词优化匹配** (去除标点、停用词后的 `clean_title + clean_artist`)
3. **纯标题搜索** (`title` only)
4. **文件名解析降级搜索** (清除括号与数字杂音)

### 2.3 增强重试与错误追踪
- **重试增强**：由最多 3 次提升到 5 次。
- **动态错误控制**：
  - Timeout / Network_error / Rate_limit：可重试
  - 404 Not Found / Parse_error：根据情况决定是否重试。
- **建立监控与反馈**：跟踪各搜索策略的成功率，将记录保存至监控队列以便按失败次数和上次尝试时间执行优先级重新抓取（优先补偿策略）。

## 3. 演进计划 (已落地的措施)
此方案对应的重试扩充、移除冷却补全机制已经在此前的核心模块重构中基本落实。后续通过 `enrichment_monitor` 和 `FailedSongsQueue` 进一步确保后台任务不被阻塞，系统可用性得到保证。
