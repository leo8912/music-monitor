# Music Monitor 后端服务架构与 API 参考

> **创建时间**: 2026-02-02  
> **版本**: v3.0 (Refactored · 2026-08-13)

本文档说明了重构后的服务层（Service Layer）核心 API、事务约定与依赖注入方式。

---

## 0. 分层架构

重构后的代码布局（Stage 1-4 完成）：

```
main.py                       # 入口：create_app + uvicorn.run(8000)
app/
  api/v1/                    # 路由层：只做参数校验/鉴权/响应模型，不写业务逻辑
  dependencies.py            # require_auth 路由级鉴权依赖
  container.py               # 依赖注入容器（服务/仓储单例的唯一出口）
  services/                  # 服务层：业务用例，全部接收 db: AsyncSession
  repositories/              # 仓储层：查询封装（joinedload/selectinload 在此声明）
  workers/                   # arq 任务 worker（队列任务注册表 tasks.py）
  notifiers/                 # 通知器（wecom / telegram）
core/
  database.py                # async engine + async_init_db（create_all + alembic）
  uow.py                     # UnitOfWork：事务边界统一管理
  queue.py                   # 队列抽象（arq↔inline 双模式）
  scheduler.py               # APScheduler 调度器
  websocket.py               # WS 广播（arq 模式走 Redis pubsub）
```

依赖方向：`api → services → repositories → models`，`api/services` 均通过
`container.py` 获取依赖，禁止在服务内部直接 `new` 其他服务（R7 修复）。

## 1. ArtistRefreshService
负责歌手歌曲列表的抓取、合并与维护。

### `refresh(db, artist_name)`
全量刷新一名歌手的歌曲资料。
- **参数**:
  - `db`: AsyncSession - 数据库会话（由路由层传入，服务不自行开 session）
  - `artist_name`: str - 歌手名
- **返回**: `int` - 新增歌曲数量
- **描述**: 核心流程包括在线拉取、智能去重、原版查找、孤儿挽救及元数据治愈。

---

## 2. FavoriteService
负责歌曲收藏状态的管理及物理文件移动。

### `toggle(db, song_id)`
切换歌曲收藏状态。
- **参数**:
  - `song_id`: int - 歌曲 ID
- **返回**: `dict` - 包含新状态和文件路径
- **文件逻辑**: 收藏时移动至 `favorites/`，取消收藏时移回 `audio_cache/`。

---

## 3. SongManagementService
负责歌曲和歌手的基础增删改操作。

### `delete_song(db, song_id)`
完全物理删除歌曲。
- **描述**: 同时删除磁盘音频文件和数据库记录。

### `redownload_song(db, song_id, source, source_id, quality=999)`
针对现有歌曲记录发起重新下载。
- **用途**: 用于修复损坏文件或升级音质。

---

## 4. ScanService
本地媒体库自动发现与清理服务。

### `scan_local_files(db, incremental=False)`
扫描本地目录并入库。
- **优化**: 引入了批量预加载和延迟提交技术，支持数万级文件的快速扫描。

---

## 5. EnrichmentService (MetadataHealer)
元数据智能补全与音质/封面升级。

### `auto_enrich_library(force=False, limit=100)`
自动执行全库标签补全任务。
- **策略**: 优先修复缺失封面和日期的记录。

### `heal_song(db, song_id, force=False, target_source=None, target_song_id=None)`
单曲元数据治愈（重构后签名）。
- **参数**:
  - `db`: AsyncSession - **必填**，不再自开 session（R1 事务边界修复）
- **描述**: 从各平台拉取元数据/歌词/封面并写回；由调用方统一管理事务。

## 6. 技术规范
- **异步支持**: 所有服务方法均为 `async`。
- **错误处理**: 核心方法均受 `@handle_service_errors` 装饰器保护，确保异常时的优雅降级；
  设置 `MM_STRICT_ERRORS=1` 可让被吞掉的异常在 CI 中原样抛出（只用于测试门禁）。
- **事务管理（UoW 语义，R1 修复后）**: 
  - 事务边界由**路由层 + UnitOfWork** 统一管理，服务方法内**不再自行 `commit()`**；
  - 需要多步写操作的服务方法（如 refresh / heal_song）接收调用方传入的 `db`，
    由调用方决定何时 `commit` / `rollback`；
  - 仓储方法（repositories/）只做查询与变更，不做提交（`get_by_*` 系列无副作用）。
- **依赖注入（R7 修复后）**: 单例统一由 `app/container.py` 的 `Container` 管理，
  通过 `get_container()` 获取；`app/services/_singletons.py` 保留为兼容层，
  转发到 Container 的便利函数（`get_download_service` / `get_aggregator` / `get_metadata_service` 等），
  新代码应直接使用 `container.py`，不再新增 `_singletons` 函数。
